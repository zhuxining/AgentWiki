## 2. P0 — 必须优先处理

### P0-1 中文全文检索事实失效

- **位置**：`repository/sqlite.py:67-73`（FTS5 未指定 `tokenize`，默认 `unicode61`）；`repository/search.py:26`（`_TOKEN_RE = r"[\w-]+"`）、`811-814`（查询侧 token 化 + `" OR "` 短语）
- **机制**：`unicode61` 不切分 CJK，连续中文串被当作**单个 token**；`_TOKEN_RE` 也把整句中文当作 1 个 token。因此查询最终变成「与文档中某个连续中文串完全相等」的短语匹配，既不是分词也不是子串。
- **实测**：正文「系统支持增量索引与向量检索能力」上，`增量索引` / `向量检索` / `配置` / `检索` / `检索系统配置方法` 全部 **0 命中**；`RRF`（英文）正常命中。端到端 `get_wiki_context("令牌")` 返回 0 条，但 `strategy` 仍报 `keyword`，**不报降级**。
- **影响**：中文 Wiki 的关键词路只覆盖标题/标签级整串。由于 semantic 是可选依赖（不可用时 `retrieval.py:103` 直接降级 keyword），**未配置 embedding 或 sqlite-vec 不可用的中文部署，检索能力接近于零**。测试用中文测切块（`test_chunking.py:25-29`）却只用英文测检索，掩盖了该缺陷。
- **建议**（两条独立路线，建议先落 1）：
  1. **FTS5 `trigram` tokenizer**：`USING fts5(..., tokenize='trigram')`。已实测本机 SQLite 3.53.4 支持，且中文子串检索成功，**零新依赖**。代价是索引体积上升、要求查询 ≥3 字符。
  2. **CJK bigram 预分词**：写入侧把 `[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]+` 段展开为 bigram 序列写入 FTS 检索列（原文另存列供 snippet 高亮），查询侧同构。质量最好，控制力最强。
  3. 无论选哪条：`_SCHEMA_VERSION` 必须递增（当前 `sqlite.py:14` = 1）以触发重建，并补「标题不含查询词、仅正文命中」的验收测试。

### P0-2 候选池无 LIMIT 且不按文档去重 → 单文档垄断、召回塌缩

- **位置**：`search.py:795-806`（exact，SQL 无 LIMIT，`806` 才 Python 切片）、`815-828`（keyword，无 LIMIT）、`847-859`（graph，无 LIMIT + DISTINCT）、`903-914`（recent，无 LIMIT）；`916-918` `_rows` 直接 `fetchall()`；`920-955` `_filtered` 在**全量行物化后**才做 scope/metadata 过滤；`retrieval.py:79` `candidate_limit = max(limit*4, 20)`
- **实测**：
  - 9 篇文档都含 `zzzq`，其中 `long.md` 有 25 个 chunk → keyword 候选池 20 槽**全部**来自 `long.md`；`limit=3`/`limit=5` 时最终结果只覆盖 **1/9** 篇文档（其余 8 篇完全进不了融合阶段）。
  - 合成 20,000 chunk 索引：exact SQL 返回 **5,555 行**换取 20 个候选；`EXPLAIN QUERY PLAN` 为全表 `SCAN` + `USE TEMP B-TREE FOR ORDER BY`。
  - MDN 场景最坏例：每个目录都有 `index.md`，查询 `index` 时 `%index%` 命中几乎全部 14,621 篇文档。
- **影响**：这是当前**最大的召回杀手**，比 RRF 公式本身严重得多；也是查询延迟的主要来源之一。
- **建议**：
  1. 每个候选 SQL 加 `LIMIT ?`（取 `candidate_limit * 4` 留过滤余量）。
  2. 过滤下推到 SQL：scope → `AND (c.path = ? OR c.path LIKE ? ESCAPE '\')`；type/tags/metadata → `json_extract(d.frontmatter_json, '$.type')`（SQLite 内置 json1）。
  3. 候选阶段文档级去重：`ROW_NUMBER() OVER (PARTITION BY c.path ORDER BY source_score) AS rn ... WHERE rn <= 3`。
  4. 验收：1 篇 25-section 文档 + 8 篇单 chunk 文档，断言 `limit=5` 时覆盖 ≥5 篇不同文档。

### P0-3 查询前全库扫描构成固定约 1.1 s 延迟

- **位置**：`indexing/sync.py:20` → `markdown/library.py:32` `sorted(self.root.rglob("*.md"))` + 逐文件 `resolve(strict=True)` + `stat()`
- **实测**：20,000 文档 1.10 s；benchmark 记录的全量 MDN（14,621 文档）查询 p50 = 1,446 ms、p95 = 1,726 ms → **约 77% 的「查询延迟」是文件系统遍历**，不是检索。
- **影响**：每次 MCP 工具调用先付 1 秒以上；延迟随库规模线性增长。
- **建议**（保留 `mtime_ns`+`size`+`hash` 一致性语义）：
  1. 目录级 `st_mtime_ns` 缓存，仅目录变化时才 `scandir` 该目录。
  2. 根快照短路：根目录 mtime + 目录集合未变时跳过 `rglob`，直接比对已索引指纹。
  3. `watch-index` 常驻时由 watcher 事件驱动，`ensure_fresh` 退化为轻量 `stat` 校验。
  4. 验收：大库空转 `ensure_fresh()` < 20 ms，且增删改仍被正确检出（现有 `test_query_preflight_indexes_native_create_update_and_delete` 必须继续通过）。

### P0-4 配置文件被静默忽略，且「只读」操作写用户家目录

- **位置**：`config.py:9` `DEFAULT_CONFIG_PATH = Path("~/.agentwiki/config.json")`；`config.py:29-55` 据此反推 `project_root = config.parent.parent`（= `~`）
- **实测**：项目级 `.agentwiki/config.json` 存在时仍加载默认值 `~/AgentWiki`；`Settings.load()` 在配置缺失时**主动创建** `~/.agentwiki/` 并写入默认配置。
- **与文档冲突**：`AGENTS.md`、`README.md:41`、`docs/MCP_TOOLS.md:6` 均声明「项目根目录 `.agentwiki/config.json`，相对路径以项目根为基准」。`tests/unit/test_config.py:40-47` 反而把家目录语义固化成了契约。
- **影响**：用户按文档放置配置完全不生效，程序去检索可能不存在的 `~/AgentWiki`（`library.py:19` 还会 `mkdir` 出一个空 Wiki）；首次运行污染家目录；只读查询产生文件写入副作用（沙箱中即表现为 `tests/unit/test_cli.py` 的 `PermissionError`）。
- **建议**（推荐 A）：
  - **A**：默认改为「先找项目根 `.agentwiki/config.json`，再回退 `~/.agentwiki/config.json`」；`Settings.load()` **只读不写**，缺失时返回默认值并输出诊断（文档根不存在时提示而非静默 `mkdir`）；同步修正 `test_config.py` 与 `test_cli.py`（补 `monkeypatch.setenv("HOME", ...)` 隔离）。
  - **B**：保留家目录语义，反向修正文档。不推荐——违背 `AGENTS.md` 明确的组织级约定。

## 3. P1 — 检索质量、benchmark 与工程门禁

### P1-1 RRF 融合丢弃全部质量信号

- **位置**：`services/retrieval.py:176-201`（`_fuse`）；写入点在 `search.py:938-942`
- **问题**：`_fuse` 只用 `enumerate` 的排名，五源统一 `1/(60+rank)`；`SearchCandidate.score` 被精心计算后**零读取者**（全仓 `grep '\.score\b'` 零命中），且四种源极性互相矛盾：exact `+1.0`、keyword `-bm25`、semantic `-(1/(1+distance))`、graph `-1.0`、recent `0.0`；`_fuse:186` 还让后遍历的源覆盖 `score`。
- **附加缺陷**：
  - recency 不是召回源，只是对**已召回集**的重排（`retrieval.py:190`），「最近有哪些变更」无法召回主题词不匹配的新文档；
  - 同文档所有 chunk 共享 `modified_at_ns`，在 recency 排序中连续占 rank → 多 chunk 文档获得 **n 倍** recency 质量；
  - `strategy` 标注失真：semantic 成功但返回空列表时仍标成 `keyword`（`retrieval.py:118`）；
  - `_RECENT_INTENT`（`retrieval.py:20-23`）无条件剥离「更新/变化/活动」，会误伤「变更管理规范」「活动图」这类主题词。
- **建议**：加权 RRF（`w={exact:1.2, keyword:1.0, semantic:1.0, graph:0.4, recency:0.3}`）；recency 改为独立召回（额外注入最新 N 篇）+ 时间衰减 `exp(-Δdays/τ)`，τ≈7–30 天；recency rank 提升到文档级；每源内按 path 去重后再融合；`strategy` 按「实际参与融合且非空的源集合」标注。

### P1-2 benchmark 无法衡量产品目标

- **位置**：`benchmarks/queries/*.jsonl`、`benchmarks/schema.py:9-19`、`benchmarks/runner.py:128,198`、`benchmarks/metrics.py`
- **问题**：
  1. 查询集仅 4–6 条、全英文，`cross_document` / `recent` / `long_document` / `robustness` **各 0 条**——产品宣称的「跨文档关系、近期变化、长文档深层章节」三项完全未测量。
  2. 全部 qrels 是 **path-only**（`"section"` 出现 0 次），导致 `recall@k ≡ document_recall@k`，而设计核心恰是「章节级证据」。
  3. **自证式耦合**：`benchmarks/README.md:98-99` 要求 section 必须等于实现自身 `" / ".join(headings)` 产出的字符串，只能证明「实现与自身一致」。
  4. 3–5 条样本报四位小数（`nDCG@5 = 0.8770`），不输出 `n`、无置信区间；README 自己也说正式集需 100–200 条。
  5. `runner.py:128` 统计的是**从不写入**的 `wiki_vectors` 表 → `IndexStats.vectors` 恒为 0，与 README §6「生成 10,463 个向量」冲突且无法自检。
  6. `runner.py:198` 的计时包含 `ensure_fresh()` 全库扫描，延迟口径不纯（见 P0-3）。
  7. 唯一 no-answer 查询用库中不存在的 token，必然 0 误报 = 恒过；且 keyword 是纯 OR，含真实词的 no-answer 查询会被命中，该指标无法发现 OR 语义问题。
  8. `query_degraded_rate` 在未配 embedding 时恒为 1.0（`retrieval.py:103` 无条件 append），指标无信号。
- **建议**：`runner.py:128` 改为 `SELECT COUNT(*) FROM wiki_vector_manifest WHERE status='ready'`；拆分 `freshness_scan_ms` 与 `retrieve_ms`；每类补 ≥20 条（含中文）；section 标注改用与实现无关的字符 span/anchor；`summarize_quality` 增加 `n` 与 bootstrap 95% CI，`n<30` 不报小数；增加 source 消融（keyword-only / +exact / +graph / +semantic / +recency）。

### P1-3 `exact` 源对多词查询恒为空，却照付全表 LIKE

- **位置**：`retrieval.py:75`（整句当 exact 查询）、`search.py:794-801`（只匹配 `d.path` / `d.title`）
- **实测**：`exact_candidates("zzzq evidence")` → 0；`exact_candidates("long")` → 20。自然的任务式查询多为多词，`%JavaScript Array methods%` 永不匹配 path/title，exact 贡献恒 0，却仍触发 P0-2 的全表扫描。
- **建议**：改为 token 级子串 OR，或对 path/title 建独立 FTS 表复用同一 tokenizer；两种都必须加 LIMIT。

### P1-4 工程门禁形同虚设

- **无任何 CI**：仓库没有 `.github/`、没有任何 `*.yml`/`*.yaml`；`AGENTS.md` 要求的 `ruff` / `ty` / `pytest` / `git diff --check` 全靠手工执行。
- **`pyproject.toml` 的 ruff 配置有实质缺陷**：
  - `fix = true` 让 `uv run ruff check`（规范指定的检查命令）**静默改写源码**，退出码 0 无法区分「干净」与「已自动修复」；实测 `ruff check --isolated --select I --diff` 报 `Would fix 11 errors`。
  - `ignore = ["unused-import"]` 是**错误的规则名**导致 F401 全局失效，注释「handled by pyflakes」恰好说反了（被禁的正是 pyflakes 的检查）。实测 `ruff check --isolated --select F401 --no-fix` 报 `search.py:7:8 F401 import operator imported but unused`。
- **integration marker 零使用**：`pyproject.toml:85-87` 声明且开启 `--strict-markers`，但 `-m integration` 收集 0 个，`-m "not integration"` 与全量结果逐字相同。规范声明的能力实际不存在。
- **建议**：建最小 CI（`ruff check --no-fix` / `ty check` / `pytest`）；移除 `ignore=["unused-import"]`；`fix` 改为 `false` 或 CI 中显式 `--no-fix`；清理 `search.py:7` 的 `operator`。

### P2-3 切块与「章节级证据 + 每文档 2 片段」不匹配

- **位置**：`indexing/chunking.py:10-11, 20-23, 64-91`；消费侧 `retrieval.py:213, 241-243`
- **具体缺陷**（均为实测，见 E11/E12）：
  1. **`_split_oversized` 突破自身 1200 上界**：`77-83` 在累加段落 + overlap 前缀后不再复核，实测 5 组输入全部越界（`(150,1200)→[150,1352]`、`(600,1049)→[600,1201]`、`(1199,1199)→[1199,1351]`）。单测 `test_chunking.py:25-29` 只覆盖单段超长。修复：overlap 取 `min(_OVERLAP_CHARS, max(0, _MAX_CHARS-2-len(paragraph)))`，append 前再复核。
  2. **空内容 chunk 被索引并可返回**：`flush()` 在「标题 + 空行 + 子标题」形态下产出 `content=""`。实测 `# Alpha\n\n## Beta\n\nbody text` → `('Alpha','')` 进入索引、参与 embedding、可返回为空 snippet 证据；纯标题文档 `# A\n\n## B\n\n### C` 更是只产出一个空 chunk。修复：`if content.strip():` 才 append。
  3. **snippet 头部截断会丢命中词**：`retrieval.py:241-243` 从 chunk 开头截 700。实测命中词位于第 703 字符时 `'ZZZQ' in snippet == False`——Agent 拿到的证据看不见查询词。修复：改用 FTS5 `snippet()`/`highlight()` 命中居中，或放宽上限。
  4. **overlap 产生同 section 重复证据**：`82-83` 的 150 字符重叠使同一章节返回两条高度重叠片段，消耗「2 片段/文档」预算；且 `section_precision_at_k` 把两条都算相关、`ndcg_at_k` 按 `(path,section)` 去重把第二条计 0——指标互相矛盾。
  5. **`_window` 小尾巴**：`step = 1050`，实测 `_window("x"*1201) → [1200, 151]`，第二块 151 字符中 150 是重复；超长单段分支完全不带 overlap，与段落累加分支行为不一致。
- **整体判断**：真正的错配是**检索单元(1200) ≠ 交付单元(700) ≠ 片段数×2**，三者无统一预算。建议按目标上下文预算（1500–2000 字符/文档）自上而下反推 chunk 大小，例如 `_MAX_CHARS=800`、`_OVERLAP_CHARS=100`、snippet ≤800。

### P2-4 异常处理与冗余约束

- **`sqlite3.IntegrityError` 未兜底**：`indexing/sync.py:74` 与 `:119` 只捕获 `(OSError, UnicodeError, ValueError)`；而移动分支 `search.py:331-334` 执行 `UPDATE wiki_documents SET path`，实测外键为**即时检查**。一旦 `wiki_chunks` 行未先清理，会抛出未捕获异常，中断整轮 `ensure_fresh`（其余文档不再索引），与「单篇失败不阻断其他文档」的可靠性承诺冲突。
- **手动删除与 FK 级联双重维护**：`sqlite.py:55` 的 `ON DELETE CASCADE` 与 `search.py:350-387` 的手工删除语义重叠，靠「先删 chunks、后 UPDATE path」的执行顺序维持正确，属隐式契约。建议注释固化该不变量，或改为 `ON UPDATE CASCADE` 让数据库接管。
- **`getattr` 特性探测绕过类型系统**：`retrieval.py:52, 129, 139` 用 `getattr` 探测端口成员，而这三人（`wait_for_initial_vector_sync` / `related_documents` / `graph_candidates`）在 `services/ports.py` 中均有正式声明。端口改名时 `ty` 不报错、运行时静默降级。建议直接调用。
- **`except BaseException` 三处**：`search.py:303, 584, 641` 会吞掉 `KeyboardInterrupt`/`SystemExit`，与规范「捕获具体异常类型」相悖。

### P2-6 并发与错误传播（专项复核的补充发现）

**H1 检索降级路径只保护 semantic，其余三路会击穿整次检索**（高）

- **位置**：`services/retrieval.py:80-94`（TaskGroup 四个 `create_task`）、`retrieval.py:154-165`（只有 `_semantic` 有 guard）
- **机制**：`exact` / `keyword` / `graph` 三路没有任何异常守卫，TaskGroup 会把异常聚合后向外重抛。
- **实测**：让 `exact_candidates` 抛 `sqlite3.OperationalError("database is locked")` →
  `RAISED: ExceptionGroup ExceptionGroup('unhandled errors in a TaskGroup', [OperationalError('database is locked')])`
- **影响**：一次瞬时 `database is locked` 会让 `get_wiki_context` 整体失败，而不是退回关键词结果；MCP 侧会把 ExceptionGroup 作为工具错误返回。违反「语义不可用时关键词仍必须可用」的降级承诺。
- **修复**：给 `exact` / `keyword` / `graph` 各加与 `_semantic` 同构的守卫（返回 `([], f"{name}_unavailable: {exc}")`），保证任何单路失败只降低策略等级。

**H2 单文档 `except` 不捕获 `sqlite3.Error`，一个文档的错误中止整轮同步**（高）

- **位置**：`indexing/sync.py:74`、`indexing/sync.py:119`
- **机制**：`_replace_document` 的 `IntegrityError`/`OperationalError` 不在 `(OSError, UnicodeError, ValueError)` 元组内，逃出循环；`get_wiki_context` 的 `ensure_fresh()` 随之失败，且该文档不会落 `sync_error`（不可观测），后续文档也不再索引。
- **修复**：两处元组补 `sqlite3.Error`，handler 内先 `mark_document_error` 再继续；`resolve_edges()`（`sync.py:80`）单独 try/except，避免抹掉整份 `SyncReport`。

**中等问题**（同一专项，按建议修复顺序）

| # | 位置 | 问题 |
| --- | --- | --- |
| M3 | `search.py:310-348` | 移动分支的 `:335-346` 三条 `UPDATE` 是**死代码**（子行已被 `_delete_document_children` 删除，恒命中 0 行）；整条移动路径依赖「先删子行」的不变量，遗漏一行即 `FOREIGN KEY constraint failed`。建议改为显式 delete+insert，删掉死代码 |

| M5 | `search.py:214-302` vs 读路径 | 读路径全部不持锁，可在文档行「已删未插」的窗口读到中间态（同一连接可见未提交状态），表现为偶发空结果或缺失图关系 |
| M6 | `search.py:504-506`、`652-654` | `asyncio.to_thread` 不可真正取消 → `close()` 后 embedding 线程仍在跑；`wait_for_vector_sync` 的 `return_exceptions=True` 静默吞掉所有向量异常 |
| M7 | `search.py:370-387` | `_delete_document_projection` 不显式删 `wiki_chunks`，完全依赖 FK CASCADE；FTS 是虚拟表无 FK，一致性只靠 `:383` 一行 DELETE 维持。建议显式删除并按 `chunk_id` 清理 FTS |
| M8 | `search.py:664-676` | `delete_paths(commit=False)` 是不提交的半成品 API（`ports.py:51` 暴露在 Protocol 上），且取消逻辑会顺带修改共享字典 |
| L9 | `sqlite.py:184-215`、`search.py:1056` | 含 DML/DDL 的 `ensure_vector_table`/`drop_vector_table` 不参与 `_write_lock`（当前仅在 `initialize` 阶段调用，属潜在缺陷） |
| L10 | `search.py:54-58`、`645-650` | `_initial_vector_sync_required` 是启动快照，首查询可能不等向量同步而降级为 keyword 且无标记 |

**明确排除的怀疑**（专项实测）：不存在真实死锁（四个取消调用点都在锁外，`close()` 不取锁；但 `asyncio.Lock` 非重入，若未来在锁内调用 `wait_for_vector_sync`/`close` 会自死锁）；`rollback()` 不会丢弃其他协程已提交的投影工作（回滚粒度在锁内、且 `_replace_document` 的提交早于向量任务进锁）。

## 附录：一句话结论

AgentWiki 的**问题定义与架构骨架值得保留**：把「从未知到已知」交给检索层、把「已知路径读写」交还 Agent 原生工具，并用可删除的 SQLite 派生投影支撑增量同步与降级，这套判断是对的。但**主干检索在中文场景下不work**（FTS 分词）、**候选池会让单篇长文档饿死其余文档**（无 LIMIT/去重）、**每次查询先花 1 秒扫全库**，这三件事决定了当前版本在真实中文 Wiki 上的可用性上限。建议按第 6 节顺序修复，其中 P0-1 与 P0-2 应视为「产品可用性」而非「性能优化」。

### B.4 后续追加：启动时初始化 AGENTWIKI.md

新建 Wiki 在启动时自动获得默认规则，避免「无规则 = 校验全过」的静默状态：

- 模板随包分发：`src/agentwiki/data/default/AGENTWIKI.md`（YAML frontmatter + 中文指导正文），
  `uv_build` 通过 `source-include` 打包；缺失配置时 `default_control_text()` 读取。
- `MarkdownLibrary.ensure_control_file()`：文件缺失才写入，返回是否发生创建；已存在的文件永不覆盖。
- 在 `runtime.create_runtime()` 中调用，因此 CLI 与 MCP（含其降级分支）的所有入口都会初始化。
- 实测：`uv build` 后安装 wheel，`default_control_text()` 可正常读取；新增 6 条测试覆盖
  模板有效性、首启生成并生效、已有文件不被覆盖、控制文件不参与索引、返回值语义。
- 副作用提示：对已有 Wiki，首次升级后会开始强制 `title/type/tags`，可能一次性出现多条
  `frontmatter.required`；调整该文件的 `required_fields` 即可放宽。

### B.6 第三轮追加：设计缺陷修复
