# AgentWiki 成熟度评估（2026-09-10）

- 评估对象：`main` @ 本轮改动（`src` 4,276 行 / 24 个模块；测试 2,140 行 / 110 个测试）
- 测量方式：`ruff check`、`ty check`、`pytest`、`sys.settrace` 行覆盖率（无新增依赖）、真实 CLI 端到端
- 结论：**核心功能已闭环，可以正常使用；工程成熟度还差两块，主要是 CI 与运维可见性。**

---

## 1. 结论速览

| 维度 | 状态 | 依据 |
| --- | --- | --- |
| 功能完备性 | **良好** | 检索五路融合、中文/多语言分词、语义阈值与弃答、索引增量同步与重建、规则治理与校验、CLI+MCP 双入口全部可用且经实测 |
| 正确性 | **良好** | 110 个测试通过；端到端实测中文命中、候选池多样性、快速路径、跨进程锁均符合预期 |
| 测试覆盖 | **不均衡** | 核心检索链路 83–96%；但 `cli.py` 47.6%、`mcp.py` 64.3%、`watcher.py` 28.6%、`locking.py` 34.4% |
| 工程门禁 | **缺失** | 无 CI。`AGENTS.md` 要求提交前手工跑 ruff/ty/pytest |
| 运维可见性 | **偏弱** | schema 升级静默删库重建，无进度、无持久"重建中"标记；无结构化 trace 与慢查询告警 |
| 性能 | **可用** | 读路径快速路径显著降低单查询开销；但 20k 文档仍有一次全树 stat（实测约 390 ms） |
| 文档一致性 | **良好** | 本轮已修掉全部已知漂移（配置路径、必填字段、治理文件名、`rank_score` 语义） |

**一句话**：作为一个"本地 Markdown 检索层"，它已经能稳定完成设计目标；作为"可持续开发的产品"，缺 CI 和运维反馈。

## 3. 需要补的内容（按优先级）

### P0 — 应当尽快补（低成本、已在多个项目验证有效）

**1. CI 门禁**

现状是零 CI，全靠 `AGENTS.md` 的"提交前必须执行"这条人工纪律。而本轮一共改了 4 次 schema、重构了两次模块分层——这类改动正是最需要自动门禁的。

最小形态（3 个 job，约 30 行 YAML）：`ruff check`（`--no-fix`）→ `ty check` → `pytest`。本项目无外部服务依赖，不需要 Postgres/Milvus 那类矩阵。

**2. 大库 schema 升级的进度与恢复**

当前 `_SCHEMA_VERSION` 不匹配时直接删除并重建，用户看不到任何输出。对 20k 文档的库，这可能是分钟级静默等待；若中途被杀，下次启动重新开始，且没有"重建中"的持久标记，失败原因也无从追溯。

建议：① 升级时输出一行说明（"index schema changed, rebuilding"）；② 在 `wiki_index_meta` 写 `rebuild_in_progress`，启动时若发现残留则报告上次重建未完成；③ 重建完成后再清标记。

**3. 入口层测试**

`cli.py` 与 `mcp.py` 是 Agent 实际接触的面，但覆盖最低。最小集：

- `cli rules` / `validate-wiki` / `sync-index` / `rebuild-index` 各一条（`CliRunner` + `--root/--index`）
- MCP `get_wiki_rules` / `validate_wiki` 各一条（`fastmcp.Client`）
- `watcher.watch_documents` 一条（标 `integration`，用真实临时目录触发一次变更）
- `locking` 的错误分支与 `remove_lock_file`

### P1 — 有价值但可等

| 项 | 价值 | 成本 |
| --- | --- | --- |
| `repository/search.py` 的向量错误/恢复分支测试 | 后台向量任务的失败路径目前只靠间接测试 | 中 |
| 异常退出后的索引一致性测试（杀进程 → 重启 → 校验） | 验证 `pending`/`error` 恢复与重建幂等 | 中（跨进程） |
| 覆盖率基线（`pytest-cov` + `fail_under`） | 防止后续退化 | 低，但需要一个新 dev 依赖 |
| 结构化检索 trace（各源候选数/耗时/被拒原因） | 调优与回归定位 | 中 |
| 慢查询告警阈值 | 大库性能回归的早期信号 | 低 |
| cross-encoder rerank | RRF 只有 rank 信号，纠正不了"两路都排第 3 但都不相关" | 中高（延迟与内存） |
| 读路径去掉全树 stat（常驻 watcher 或目录快照持久化） | 20k 文档每查询省约 390 ms | 中高（复杂度） |

### P2 — 按需再做

- 多语言 embedding 选型（当前默认 `bge-small-en-v1.5` 对中文语义无效；本轮已用阈值兜住假阳性）
- embedding identity 逐 chunk 持久化（模型变化目前整表重嵌）
- 结果分页（`total` / `offset`）
- watcher 做深（ignore 规则、状态落盘、周期重启、批量移动配对）
- 多进程并发写的写入侧 CAS（当前用索引级文件锁串行化）

## 4. 明确不需要补的（避免过度建设）

| 项 | 理由 |
| --- | --- |
| alembic / 逐列迁移 | 索引是**可删除派生物**，重建比迁移更符合"Markdown 是事实源"；唯一反转条件是引入不可重建状态 |
| 多项目 / 多 workspace 路由 | 本地单机单 Wiki 用 `scope` 已够；同类项目为此付出 2,039 行 + 3,589 行测试 |
| Redis / 外部读缓存 | 单用户单进程，重复读的瓶颈在目录扫描而非 DB |
| Postgres / pgvector / Milvus 后端 | 不是当前产品承诺 |
| 服务端写入工具族 | 会摧毁"增删改归 Agent 原生工具"这条边界 |
| 云端同步 / Web UI / HTTP API | 同上 |

## 5. 一个必须说清的风险

**`_SCHEMA_VERSION` 已到 4，且本轮改了 4 次 schema。** 每次不匹配都会删除并重建索引。对 Markdown 内容没有风险，但对大库意味着每次升级后的首次启动都要承担一次全量重建，且当前**没有任何输出或进度**。如果已有真实库在使用，建议先补第 3.2 项（进度与恢复标记）再继续演进 schema。

---

## 6. 建议的下一步顺序

1. **CI 三件套**（ruff / ty / pytest）——把人工纪律变成自动门禁
2. **schema 升级的进度与 `rebuild_in_progress` 标记**——消除静默长等待与失败不可追溯
3. **入口层测试补齐**（CLI 5 个命令 + MCP 2 个工具 + watcher + locking 错误分支）
4. 覆盖率基线 + 向量错误分支测试
5. 其余按实际使用反馈决定

前三项合计约半天工作量，能把"能用"提升到"可长期维护"。

## 7. 第三批落地（本轮）

### 已做

| 项 | 结果 |
| --- | --- |
| **Makefile / CI 门禁单一入口** | 新增 `Makefile`：`make check` = lint + type + test-unit + integration。CI 与本地共用同一批目标，避免两边漂移。`AGENTS.md` 已改为要求 `make check` |
| **中文可用的 embedding 模型** | 默认模型从 `BAAI/bge-small-en-v1.5`（英文单语）换成 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`（384 维 / 约 220 MB，多语言）。实测中文改写查询 **4/4 命中**，无关查询被拒绝 |
| **相似度阈值重新标定** | 从英文模型的 0.55 降到 **0.30**：实测真实改写命中 0.34–0.58、无关查询峰值 0.10。阈值随模型变化，已在 `README` 标注"换模型必须重新标定" |
| **schema 升级可见性与恢复** | 升级时输出原因与被发现/当前版本；写 `{index}.rebuild.json` 标记；同步完成即清除；若上次重建中断，下次启动以 warning 报告中断时间 |
| **语义检索回归测试** | 新增 8 条（含 4 条中文改写）。它们正是为了守住本轮修掉的三个 bug——假向量测试看不见这些 |
| **测试资源按 marker 隔离** | 「真实 ONNX 模型」与「派生子进程」两类测试互不共存于同一进程，各自标记 `integration`；`make check` 分两次 pytest 运行，彻底消除了进程退出阶段的 `libc++abi` 崩溃 |

### 本轮修掉的三个真实缺陷（都由新增测试暴露）

1. **相似度符号双重取负**：SQL 取 `-(cosine)`、Python 端又取一次负，导致相似度恒为负数 → **阈值一直在拒绝所有语义候选**。语义检索实际上从未生效。
2. **`selected_rank` 没有投影**：`_candidate_sql` 外层 SELECT 未包含该列，取值恒为默认 0.0，阈值判断彻底失效。
3. **阈值与模型不匹配**：0.55 是英文模型的值，对多语言模型会拒掉全部正确结果（正确命中仅 0.34–0.58）。

第 1、2 条是我前两轮引入的，且**当时的测试全部通过**——因为阈值过滤路径没有被任何测试覆盖。这是本轮最值得记的教训：加机制必须同时加"机制生效"的测试。

| CLI 五个命令的测试 | `cli.py` 行覆盖仍约 48% |
| MCP `get_wiki_rules` / `validate_wiki` 的测试 | `mcp.py` 行覆盖仍约 64% |

## 8. 第四批落地：入口层测试与覆盖率门禁

### 结果

| 指标 | 之前 | 现在 |
| --- | ---: | ---: |
| 测试总数 | 119（111 unit + 8 integration） | **148**（139 unit + 9 integration） |
| 行覆盖率（`agentwiki` 全包） | 未测量 | **90.68%**（门槛 88%） |
| `cli.py` | 47.6% | 通过 15 条命令级测试覆盖 |
| `mcp.py` | 64.3% | **98%**（含 lifespan 复用与降级分支） |
| `runtime/watcher.py` | 28.6% | 注入式事件流 + 1 条真实 watcher 集成测试 |
| `indexing/locking.py` | 34.4% | 83%（含不可写路径降级、释放幂等） |

### 新增测试文件

- `tests/unit/test_cli.py`（15 条）：`query`（含 metadata 错误分支）、`sync-index`、`rebuild-index`、`rules`（含 scope）、`validate-wiki`（单文件 / `--full` / 未索引路径 / 缺字段）、scope 越界拒绝、已删除命令不再暴露。
- `tests/unit/test_mcp.py`（7 条）：三个工具各自的返回体、无匹配时 `matched=false`、`--full` 校验、缺字段报告、scope 参数、**lifespan 运行时复用**与**降级分支自建运行时并在退出后关闭连接**。
- `tests/unit/test_watcher.py`（5 条 unit + 1 条 integration）：`.md` 过滤（含大小写）、每批触发一次同步、`stop_event` 短路、真实 watchfiles 端到端。
- `tests/unit/test_locking.py`（6 条 unit + 1 条 integration）：获取/释放、不可写路径降级为不加锁、缺失目录自动创建、未持有时释放是 no-op、`remove_lock_file` 幂等、跨进程互斥。

### 覆盖率门禁

`pyproject.toml` 的 pytest `addopts` 加入 `--cov=agentwiki --cov-fail-under=88`；`make check` 分两批运行（unit 计覆盖率、integration 用 `--no-cov` 独立进程）。门槛设在**当前值下方约 2.7 个百分点**：既容忍平台差异，又能拦住真实退化。

### 过程中修掉的两个测试设计错误

1. **同进程嵌套 `flock` 会永久阻塞**：我最初写了一条"同进程二次获取"的测试，直接把测试套件挂死。跨进程互斥必须用子进程验证，且要带 `asyncio.timeout` 保护。
2. **无意义断言**（`assert Path`、`assert callable(...)`）只是凑覆盖率，已删除。
