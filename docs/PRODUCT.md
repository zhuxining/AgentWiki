# AgentWiki MVP 产品文档

> 状态：MVP 定义稿
> 
> 本文定义 AgentWiki 的产品定位、首个用户闭环和范围。工程边界以 [架构与迁移方案](ARCHITECTURE.md) 为准，协议行为以 [MCP 契约](MCP_TOOLS.md) 为准。

## 1. 产品定位

AgentWiki 是一个**由用户与 AI agent 共同编辑、面向 agent 检索的本地 Markdown Wiki**。

Markdown 和 YAML Frontmatter 是唯一事实源；AgentWiki 将分散的 Wiki 内容解析、索引并以带来源的证据返回给 agent。用户和 agent 如何写入、确认、归档知识，由官方或社区 Skill 以及可选 Hook 引导；AgentWiki 核心不擅自决定知识内容。

### 核心承诺

> 用户维护一套可读、可迁移、可纠正的 Wiki，agent 在任务中能够找到并使用正确的项目知识、用户规范和记忆。

### 知识范围

MVP 不限制 Wiki 存储的内容，但通过目标标签区分作用域：

- `project:<name>`：项目规则、架构、命令、决策和项目经验；
- `user`：适用于用户所有项目的规范、偏好和工作方式；
- `memory`：事实、经验、事件和其他可复用记忆；
- 未声明目标：允许保存，但检索时不作为高优先级约束。

建议同时使用 `type` 和 `status` 等 Frontmatter 字段表达知识类型及确认状态。自由标签不能替代受约束的目标字段。

## 2. 用户与问题

### 目标用户

个人开发者及经常使用 AI agent 的个人用户，尤其是使用 coding agent、CLI agent 或 MCP agent 的用户。

### 用户问题

用户的项目规则、通用工作规范和历史记忆散落在 `AGENTS.md`、README、Markdown 文件、代码、多个项目和对话中。用户不得不在每次任务中重复解释；agent 即使完成过类似任务，也可能找不到或误用已有知识。

用户也不愿意把记忆交给不可见的自动系统：错误知识一旦被自动写入，后续任务会持续受到污染。因此知识必须可读、可编辑、可追溯，并允许用户和 agent 采用不同的写入确认策略。

### 当前替代方案

- 在 `AGENTS.md` 中手写规则；
- 用户在每次对话中重复说明；
- 使用 `rg`、代码搜索或手工浏览文件；
- 使用通用笔记、知识库或向量检索工具。

这些方式分别缺少统一检索、跨任务复用、证据回读或可控的 agent 协作编辑流程。

## 3. MVP 用户闭环

```text
用户编辑或创建 Markdown
  → AgentWiki 增量同步并建立索引
  → agent 主动调用或由 Hook 触发检索
  → AgentWiki 返回相关章节、作用域和原文证据
  → agent 完成任务
  → Skill 生成知识新增/修改建议，或按策略直接写入
  → 用户继续编辑、确认或纠正
  → 下一次任务复用知识
```

### 首个主场景

用户在一个已有 Wiki 的项目中启动任务。agent 通过官方 Skill 或 MCP 工具检索项目知识和用户级规范，获得带路径、章节和原文片段的上下文；任务结束后，Skill 引导 agent 将新的项目事实或决策整理到 Wiki。

MVP 首先证明项目知识闭环；用户规范和记忆保留为同一检索模型中的第二、第三类内容，不要求首版为每类建立完全不同的界面或存储系统。

## 4. 产品原则

1. **Markdown 是事实源**：索引和元数据可以删除、重建，不能反向成为唯一事实。
2. **用户与 agent 共同编辑**：用户可直接改 Markdown，agent 可按 Skill 提议或写入。
3. **核心提供检索，不强制治理流程**：确认、自动写入和归档策略属于 Skill。
4. **证据优先**：检索结果必须可回读到路径、章节和原文片段。
5. **作用域明确**：当前任务优先使用项目知识，再合并用户规范和相关记忆。
6. **自动化可降级**：语义索引或其他派生能力失败时，关键词检索仍应可用。

## 5. 目标与非目标

### 目标

- 让 agent 能按当前项目或用户作用域检索未知位置的 Markdown 知识。
- 让检索结果包含足够证据，使 agent 能回读原文而不是依赖无来源摘要。
- 支持主动检索和可选生命周期 Hook 两种接入方式。
- 允许官方及社区 Skill 在同一 Wiki 上实现项目知识、用户规范和记忆等不同写入策略。
- 保持本地优先、可迁移和不依赖云端模型或服务。

### 非目标

- 不提供 Web UI、HTTP API 或云端同步。
- 不把 AgentWiki 做成自动替用户决策的长期记忆黑盒。
- 不强制所有知识采用同一种确认、分类或写入流程。
- 不由核心自动抽取实体、总结对话或写入 Markdown。
- 不在 MVP 中解决多用户权限、团队协作和跨设备合并。

## 6. 用户故事

### 个人用户

- 作为个人用户，我想把项目规则、用户规范和记忆放在同一个 Wiki 中，以减少跨工具维护。
- 作为个人用户，我想直接编辑 Markdown，以便掌控事实、迁移数据并纠正 agent。
- 作为个人用户，我想看到 agent 使用知识的来源，以便判断结果是否可信。
- 作为个人用户，我想让不同 Skill 采用不同的写入策略，以便高风险规则需要确认、低风险记忆可以自动沉淀。

### Agent / Skill 开发者

- 作为 Skill 作者，我想按 scope、标签和类型检索知识，以便为当前任务提供相关上下文。
- 作为 Skill 作者，我想通过 MCP 或 CLI 主动查询 AgentWiki，以便不依赖固定的上下文注入流程。
- 作为插件作者，我想在会话或任务生命周期中触发检索，以便实现自动提供上下文的工作流。
- 作为社区 Skill 作者，我想复用统一的检索和证据结构，以便实现不同的知识写入和治理策略。

## 7. MVP 需求

### P0：必须具备

#### P0.1 Wiki 索引与增量同步

- 扫描 Wiki 下的 Markdown 文档，排除规则入口文件 `AGENTWIKI.md`。
- 解析 Frontmatter、标题层级、章节、内部链接和文件修改信息。
- 支持增量同步、删除、移动识别、失败隔离和可重试恢复。
- 索引失败不得覆盖原文或误报为删除。

**验收：**新增、修改、删除或移动文档后，下一次查询能够反映新状态；单篇解析失败不阻塞其他文档，且下次仍会重试。

#### P0.2 主动检索

- 支持关键词检索、精确匹配、近期查询和可选语义/混合检索。
- 支持 `scope`、目标标签、文档类型和元数据过滤。
- 支持空查询返回近期文档。
- 返回路径、标题、章节、片段、命中来源、修改时间和必要的关系信息。

**验收：**agent 可以按项目 scope 查询；结果包含可回读的原文证据；无匹配时明确返回无匹配，而不是伪造故障或答案。

#### P0.3 MCP / CLI 接入

- MCP 提供上下文检索、规则获取和 Wiki 校验工具。
- CLI 提供索引、查询、配置和校验入口。
- MCP 与 CLI 使用同一 AgentWiki 异步用例门面和同一检索行为。

**验收：**MCP 工具可在 stdio 下完成初始化、列表和查询；CLI 与 MCP 对相同 Wiki 返回一致的核心结果语义。

#### P0.4 证据与安全边界

- 结果携带路径、章节和原文片段，提示 agent 在形成结论前回读关键原文。
- scope、路径和过滤参数经过校验，拒绝越界路径和非法表达式。
- 正常无匹配不进入 degraded；真正的索引或模型故障必须报告。

**验收：**越界路径和非法请求返回错误；正常查询结果不会把 rank score 伪装为概率或事实可信度。

#### P0.5 规则校验

- 获取 Wiki 规则并按 scope 合并。
- 默认只报告问题；格式修复必须显式请求。
- 校验支持必填字段、路径、标签、链接和 Markdown 格式问题。

**验收：**默认校验不修改文件；显式格式修复前后重新校验，并在外部文件变化时跳过写回并报告冲突。

### P1：首个闭环后的增强

- 官方默认 Skill：项目上下文、用户规范、记忆。
- Hook 触发的有限上下文检索：会话开始、任务开始或任务结束。
- 检索结果按目标作用域和知识状态进行更明确的优先级组织。
- 固定语料上的关键词与混合检索质量基准。
- 变更建议摘要和更方便的用户确认流程，但不引入独立 Web 编辑器。

### P2：未来考虑

- 社区 Skill 分发和版本管理。
- 更丰富的 Hook 生命周期协议。
- 多 Wiki 合并检索、跨项目关系和团队共享。
- 内容历史、审计和冲突可视化。
- 其他 embedding 模型和更大规模 Wiki。

## 8. 检索与作用域规则

默认任务上下文按以下顺序组合：

```text
当前用户指令 > 当前项目规则 > 用户级规范 > 已确认记忆 > 草稿/临时记忆
```

这只是默认检索优先级，不是核心替用户裁决冲突。Skill 可以根据场景改变策略，但必须显式声明 scope 和来源。

目标字段应使用受约束的 `user` 或 `project:<name>`；未识别目标可以保存，但默认降权。自由标签用于补充筛选，不承担作用域和优先级语义。

## 9. 编辑策略

AgentWiki 核心不直接决定知识写入策略。官方或社区 Skill 可以选择：

- **建议模式**：agent 输出新增、修改或删除建议，由用户确认后使用原生文件工具写入；
- **自动模式**：Skill 对低风险内容直接写入，但必须保留来源、时间和可识别的变更信息。

两种模式都必须遵守项目既有的安全写回、冲突检测和 Markdown 事实源约束。MVP 不要求 AgentWiki 自建编辑器或审批系统。

## 10. 成功指标

由于当前缺少真实用户基线，以下是首轮验证目标，不是已承诺的长期业务指标：

### 领先指标

- **核心闭环完成率**：试用用户中，完成“写入 → 检索 → 复用”闭环的比例，目标 ≥ 70%。
- **检索可用率**：标注的相关查询中，前 3 个结果包含目标文档的比例，目标 ≥ 80%。
- **证据完整率**：有效结果包含路径、章节和原文片段的比例，目标 100%。
- **检索失败降级**：语义能力不可用时，关键词检索仍能返回可用结果；不得因向量失败导致全库不可用。
- **用户纠正成本**：用户确认或纠正一条 agent 知识建议的中位时间，首轮目标 ≤ 30 秒。

### 滞后指标

- 连续使用两周后，用户主动维护 Wiki 的频率；
- 用户在重复项目任务中减少手工解释的次数；
- agent 因违反已记录项目规则而被用户纠正的次数变化。

指标应通过真实任务记录、固定查询集和用户访谈共同验证，不以检索调用次数单独代表价值。

## 11. 开放问题

- **[产品/工程，非阻塞]** 目标标签的具体 Frontmatter 字段名是否固定为 `target`，还是沿用现有 `tags` 与 `metadata` 组合？
- **[产品]** 官方默认 Skill 是否随 AgentWiki 发布，还是作为独立仓库维护？
- **[工程]** Hook 是否由外部 agent 插件实现，AgentWiki 是否只需要保证 MCP 调用稳定？
- **[产品/工程]** 自动写入的低风险记忆是否需要统一状态字段，还是完全交由 Skill 定义？
- **[数据]** 首轮真实用户和固定查询集如何建立，以便替代当前小样本检索基准？
- **[产品]** MVP 首发优先支持哪一种 agent 宿主：coding agent、通用 CLI agent，还是 MCP 客户端？

## 12. 分阶段计划

### Phase 1：检索基础

稳定本地 Wiki 扫描、增量索引、作用域过滤、关键词检索、证据返回和 MCP/CLI 接入。

### Phase 2：首个 agent 闭环

提供项目上下文 Skill；支持任务开始主动检索和任务结束知识整理建议。使用一个真实代码项目验证闭环和指标。

### Phase 3：扩展知识策略

加入用户规范与记忆 Skill，补充 Hook 示例、状态/优先级策略和社区 Skill 编写约定。

### MVP 退出标准

只有同时满足以下条件，才认为 MVP 完成：

- 一个真实项目可以从 Markdown 写入到 agent 检索再到知识复用；
- 检索结果具备稳定、可回读的证据；
- 索引或语义能力失败不会破坏原文和关键词能力；
- 项目知识、用户规范和记忆可以通过目标标签区分；
- 至少一种建议式 Skill 和一种自动式 Skill 策略经过真实任务验证；
- P0 验收项通过，且固定语料基准结果已记录。
